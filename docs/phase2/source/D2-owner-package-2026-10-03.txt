# ADR-P2-001: اعتماد D2 كمسار تحليلي وتاريخي مستقل

## الحالة

ACCEPTED_IN_PRINCIPLE

Implementation Status:
NOT_STARTED

Provider Decision:
NOT_SELECTED

Effective Phase:
PHASE-2 DISCOVERY AND BASELINE ONLY

## السياق

تستخدم منصة ميزان المالي D1 بوصفها قاعدة البيانات التشغيلية الدائمة.

تحتوي D1 حاليًا على بيانات تشغيلية، تشمل:

- المحافظ والأرصدة والمراكز.
- عمليات الشراء والبيع.
- التوقعات المحفوظة ونتائج تقييمها.
- إعدادات الموقع وسجل تعديلها.
- بيانات المصادر وقوائم المتابعة.
- سجلات التشغيل والمهام الدورية.

يتوقع أن يؤدي نمو تاريخ التوقعات، ولقطات المصادر، وتجارب النماذج،
والـBacktesting، وسجلات التقييم، والأبحاث المستقبلية إلى زيادة حجم
وأنواع البيانات التي لا يحتاج التطبيق التشغيلي إلى قراءتها لحظيًا.

## القرار

يُعتمد D2 كمسار تخزين مستقل مكمل لـD1.

D1 تبقى مصدر الحقيقة التشغيلي.

D2 تصبح مصدر الحقيقة التحليلي والتاريخي للبيانات التي تُنقل إليها
وفق عقود نقل وإصدارات وبصمات قابلة للتتبع.

D2 لا تستبدل D1 في هذه المرحلة.

## حدود المسؤولية

### D1 تملك

- الحالة التشغيلية للمحافظ.
- النقد والمراكز الحالية.
- سجل الصفقات القانوني داخل التطبيق.
- الإعدادات الحالية.
- حالة عمليات الموقع.
- التوقعات النشطة التي يحتاجها التطبيق.
- قواعد التحكم والصلاحيات.

### D2 تملك

- نسخ البيانات الخام التاريخية.
- مجموعات البيانات التحليلية.
- نتائج الـBacktesting.
- تشغيلات الأبحاث.
- تقييمات النماذج طويلة الأجل.
- لقطات التوقعات المكتملة والناضجة.
- التحليلات التجميعية التي لا تغيّر الحالة التشغيلية.

## القيود

- لا كتابة مباشرة من D2 إلى جداول D1 التشغيلية.
- لا نقل لبيانات D1 قبل وجود عقد نقل موثق.
- لا حذف من D1 بمجرد نجاح النسخ إلى D2.
- لا تعتبر البيانات منقولة حتى تنجح مقارنة العدد والبصمة والهوية.
- لا تستخدم D2 لاتخاذ قرار تشغيلي حي قبل اعتماد عقد قراءة واضح.
- لا تُخزن أسرار أو رموز وصول داخل D2.
- لا تُنقل بيانات حساسة دون سياسة وصول واحتفاظ وحذف معتمدة.
- لا تعتمد التقنية المادية لـD2 ضمن هذا ADR.

## نمط النقل

النمط الافتراضي:

COPY → VERIFY → RETAIN → REVIEW → OPTIONAL ARCHIVE

وليس:

MOVE → DELETE

## هوية كل سجل منقول

يجب أن يحتفظ السجل المنقول، عند انطباق ذلك، بالحقول التالية:

- sourceSystem
- sourceTable
- sourceRecordId
- sourceVersion
- sourceCreatedAt
- sourceUpdatedAt
- exportedAt
- transferBatchId
- schemaVersion
- contentHash
- provenance
- classification

## الكتابة العكسية

أي نتيجة من D2 يراد إدخالها إلى D1 يجب أن تمر عبر:

1. عقد نتيجة معتمد.
2. Validation.
3. مقارنة خارج العينة عند انطباق ذلك.
4. مراجعة بشرية أو بوابة ترقية معتمدة.
5. سجل قرار مستقل.

## ما لا يحسمه هذا القرار

هذا القرار لا يحدد:

- المنتج أو المزود المستخدم لتنفيذ D2.
- سياسة الاحتفاظ النهائية.
- مدة الاحتفاظ.
- RPO أو RTO.
- تكاليف التشغيل.
- تشفير البيانات ونسخها الاحتياطية النهائية.
- جدول النقل الدوري.
- التاريخ الذي يمكن فيه حذف بيانات من D1.

## البدائل التي نوقشت

### إبقاء جميع البيانات في D1

مقبول حاليًا، لكنه قد يخلط الحالة التشغيلية مع التاريخ البحثي والتحليلي.

### استبدال D1 بالكامل بـD2

مرفوض في هذه المرحلة، لأن D1 قاعدة التشغيل الحالية، ولم تُثبت حاجة
أو فائدة الاستبدال.

### تقسيم المسؤوليات بين D1 وD2

مقبول من حيث المبدأ، بشرط تنفيذ تدريجي قائم على العقود والأدلة.

## العواقب الإيجابية

- عزل أعباء البحث والتحليل عن بيانات التشغيل.
- الحفاظ على تاريخ طويل للتوقعات والتقييمات.
- تسهيل إعادة الإنتاج والـBacktesting.
- تقليل خلط البيانات البحثية بالقرارات التشغيلية.
- توفير مسار نمو دون تغيير D1 مباشرة.

## المخاطر

- ازدواج الحقيقة بين D1 وD2.
- فقد أو تكرار سجلات أثناء النقل.
- اختلاف المخططات والإصدارات.
- قراءة بيانات غير مكتملة من D2.
- كتابة نتائج بحثية إلى التشغيل دون اعتماد.
- زيادة التعقيد التشغيلي والتكلفة.

## بوابة التنفيذ

لا يبدأ تنفيذ D2 حتى تكتمل:

- D2 technology decision.
- Data classification.
- Migration contract.
- Transfer identity specification.
- Reconciliation tests.
- Access policy.
- Retention policy.
- Failure and retry policy.
- Phase-2 human approval.

# ADR-P2-001
# D2 Data Platform

Status:
ACCEPTED_IN_PRINCIPLE

Phase:
PHASE-2

Wave:
TRUST

Date:
2026-10-03

---

## Context

D1 is the current operational source of truth for Mizan Financial.

D1 currently stores:

- Portfolios
- Cash balances
- Buy/Sell transactions
- Forecasts
- Forecast evaluations
- Site settings
- Watchlists
- Source metadata
- Operational logs

As historical data grows, especially:

- Forecast history
- Evaluations
- Backtesting
- Research datasets
- AZIZ future artifacts
- Mizan Score future artifacts

a secondary data platform is required.

---

## Decision

D2 shall be introduced as:

Historical + Analytical Data Platform

D1 remains:

Operational Source of Truth

D2 does not replace D1.

D2 complements D1.

---

## Responsibilities

### D1

Operational State

- portfolios
- positions
- balances
- trades
- active forecasts
- settings
- watchlists
- operational logs

### D2

Historical State

- source snapshots
- research datasets
- forecast history
- forecast evaluations
- backtesting results
- model evaluations
- analytical datasets
- future AZIZ artifacts
- future Mizan Score artifacts

---

## Migration Rule

Default rule:

COPY
→ VERIFY
→ RETAIN
→ REVIEW

Never:

MOVE
→ DELETE

---

## Source Of Truth

D1 remains authoritative for operational workflows.

D2 remains authoritative for historical analytics.

---

## Constraints

- No direct writes from D2 into D1.
- No deletion from D1 after export.
- Every transferred batch must be verifiable.
- Every transferred batch must have hashes.
- Every transferred batch must have lineage.

---

## Future Review

This ADR does not determine:

- D2 technology
- D2 hosting vendor
- retention policy
- backup policy
- access model
- cost model

These decisions will be handled separately.

---

ACCEPTED_IN_PRINCIPLE

Implementation:
NOT_STARTED

PRAGMA foreign_keys = ON;

-- =====================================================
-- Source Snapshots
-- =====================================================

CREATE TABLE source_snapshots (
    snapshot_id TEXT PRIMARY KEY,
    source_name TEXT NOT NULL,
    snapshot_time TEXT NOT NULL,
    content_hash TEXT NOT NULL,
    schema_version TEXT,
    created_at TEXT NOT NULL
);

CREATE INDEX idx_source_snapshots_time
ON source_snapshots(snapshot_time);

-- =====================================================
-- Source Files
-- =====================================================

CREATE TABLE source_files (
    file_id TEXT PRIMARY KEY,
    snapshot_id TEXT NOT NULL,
    symbol TEXT NOT NULL,
    market TEXT NOT NULL,
    dataset_hash TEXT NOT NULL,
    created_at TEXT NOT NULL,

    FOREIGN KEY(snapshot_id)
    REFERENCES source_snapshots(snapshot_id)
);

CREATE INDEX idx_source_files_symbol
ON source_files(symbol);

CREATE INDEX idx_source_files_snapshot
ON source_files(snapshot_id);

-- =====================================================
-- Forecast History
-- =====================================================

CREATE TABLE forecasts_history (
    forecast_id TEXT PRIMARY KEY,
    symbol TEXT NOT NULL,
    model_version TEXT NOT NULL,
    issued_at TEXT NOT NULL,
    prediction_payload TEXT NOT NULL,
    source_snapshot_id TEXT,

    FOREIGN KEY(source_snapshot_id)
    REFERENCES source_snapshots(snapshot_id)
);

CREATE INDEX idx_forecast_symbol
ON forecasts_history(symbol);

CREATE INDEX idx_forecast_issued
ON forecasts_history(issued_at);

-- =====================================================
-- Forecast Evaluations
-- =====================================================

CREATE TABLE forecast_evaluations (
    evaluation_id TEXT PRIMARY KEY,
    forecast_id TEXT NOT NULL,

    reference_price REAL,
    realized_price REAL,

    error_percent REAL,

    direction_correct INTEGER,
    horizon_days INTEGER,

    evaluated_at TEXT,

    FOREIGN KEY(forecast_id)
    REFERENCES forecasts_history(forecast_id)
);

CREATE INDEX idx_eval_forecast
ON forecast_evaluations(forecast_id);

-- =====================================================
-- Backtest Runs
-- =====================================================

CREATE TABLE backtest_runs (
    run_id TEXT PRIMARY KEY,

    model_version TEXT NOT NULL,
    dataset_version TEXT NOT NULL,

    parameters_json TEXT NOT NULL,

    executed_at TEXT NOT NULL
);

CREATE INDEX idx_backtest_model
ON backtest_runs(model_version);

-- =====================================================
-- Backtest Results
-- =====================================================

CREATE TABLE backtest_results (
    result_id TEXT PRIMARY KEY,

    run_id TEXT NOT NULL,

    accuracy REAL,
    precision_score REAL,
    recall_score REAL,
    f1_score REAL,

    sharpe_ratio REAL,
    win_rate REAL,
    max_drawdown REAL,

    FOREIGN KEY(run_id)
    REFERENCES backtest_runs(run_id)
);

CREATE INDEX idx_backtest_result_run
ON backtest_results(run_id);
