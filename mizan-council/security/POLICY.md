# سياسة أمان مجلس ميزان v1

## مبدأ أقل صلاحية

كل وكيل يحصل على أقل قدر من السياق والأدوات اللازمة لمهمته. لا تُرسل مفاتيح API أو أوزان خاصة أو Artifacts حساسة في المحادثات أو GitHub.

## ما يُمنع في v1

- أي وصول مباشر لبيئة إنتاج ميزان.
- أي Merge أو Deploy تلقائي.
- أي كتابة إلى الفرع المعتمد دون موافقة Owner.
- أي تخزين لمفاتيح المزودين في ملفات tracked.
- أي كشف لعتبات أو أوزان خاصة في ردود العميل أو logs العامة.

## الأسرار

- `.env` محلي وغير tracked.
- LiteLLM يحتفظ بمفاتيح المزودين في البيئة/Secret Manager، وليس في Flowise nodes قدر الإمكان.
- مفتاح LiteLLM الداخلي مستقل عن مفاتيح المزودين.
- مفتاح تشفير Credentials في Flowise مستقل عن كل ما سبق.
- عند الإنتاج: نقل الأسرار إلى Secret Manager وتدويرها دوريًا.

## الشبكة

النسخة الأولى تربط Flowise وLiteLLM بـ `127.0.0.1` فقط. لا تُفتح المنافذ للعامة. عند النشر الخارجي، توضع خلف طبقة وصول موثقة مثل reverse proxy/Zero Trust مع TLS، ولا يعتمد الأمان على معرفة الرابط وحدها.

## Human-in-the-loop

تتطلب موافقة Owner قبل:

- Merge.
- Deploy.
- حذف بيانات أو ملفات.
- استخدام Secret جديد أو توسيع صلاحيات أداة.
- تشغيل أداة يمكنها الكتابة خارج فرع التجربة.

## فصل المهام

- Developer يكتب ولا يعتمد.
- Verifier يختبر ولا يصلح النتائج أثناء الاختبار.
- Critic وResearcher لا يملكان write access للكود.
- Manager ينسق ولا يتجاوز حاجز Owner.

## التسجيل

يحفظ المجلس metadata كافية لإعادة التحقق: task id، model alias، timestamps، repo ref/commit، نتيجة الأدوات، وحالة الموافقات. لا تسجل payloads حساسة أو Secrets.

## قاعدة الفشل الآمن

عند فقد التوثيق أو السياق أو صلاحية الإعدادات أو فشل أداة التحقق: الحالة الافتراضية هي **STOP / REVIEW REQUIRED**، لا الاستمرار التلقائي.
